## Take, in priority order
1. **`/no-comments` + Comment Sicko (adversarial comment pruning).** A read-only subagent (`comment-sicko`) scans a diff or scope for narration, banners, commented-out code, and workaround-justifying comments, and kills everything except five named exceptions (legal headers, genuinely external non-obvious behavior, `prettier-ignore`, public-API doc comments, an RFC/issue link explaining a constraint code can't express). The parent skill (`no-comments`) then rejects bad deletions, re-runs a sloppy pass once, fixes trivial accepted flags directly, and escalates anything needing a real fix to a design step. This is close to this project's own house style (`CLAUDE.md`: "default to writing no comments... only add one when the WHY is non-obvious") but turns the preference into an actual adversarial review pass instead of a prose reminder, with a named exception list instead of "use your judgment." Candidate: a framework skill, reviewed by a Build Engineer's own PR before merge, or folded into the convergence loop as a dedicated pass distinct from logic review.
2. **Swarm's evidence-rejection rule.** "Drop a result that does not record the SHAs and method its brief names, and respawn that worker once. After a second miss, record a gap. A gap does not count as a pass." This is a sharper, more general version of what `tools/class-ledger` already does for `verify-class` (a close-out needs an evidence pointer). Candidate: fold the same drop-and-respawn-once rule into the convergence loop's round protocol (`docs/multi-orchestrator-model.md` or the class-ledger tool itself) so a worker's unverifiable claim never silently counts as done.
3. **Fresh-subagent-by-default.** "Give new work to a fresh subagent with consolidated scope... Resume... only when the new work strictly needs state that lives in that agent and is costly to move (local checkout, uncommitted changes, a process it still runs)... Interrupt-chained resumes silently drop directives." We don't currently say this anywhere. Candidate: a short protocol note for Build Engineer re-rounds, since our own convergence loop already fixes a reported instance per round and a resumed agent silently dropping an earlier directive would look exactly like a repeated-instance leak we'd otherwise blame on the reviewer.
4. **Eval playbook (blinded before/after).** "Test how a skill or prompt change affects agent behavior, blinded." We have no process for testing whether a skill-file edit (like the one just proposed in PR #1 on this repo) actually changes agent behavior versus just reading better to a human. Candidate: later, once F6's rule-to-enforcer table exists; a blinded eval is a bigger lift than a rule addition.
5. **Unslop checklist.** A concrete, numbered list of AI-writing tells (filler phrases, em dashes, title case, "not just X but Y," vague attributions) for cleaning up prose. Low risk, no behavior change. Candidate: cite from our own PR-description and `decisions.md` writing guidance, not a new skill.
6. **Benchmark-checklist.** "Vets the number (limiter, tuning, errors, repeat runs, end-to-end relevance) before you report or act on it." Directly relevant once F3's own metrics goal (rounds per PR, classes per PR, tokens and dollars) starts producing real numbers to put in `decisions.md`. Candidate: later, when we first report a measured improvement.

## Leave
The rest of `poteto-mode` is a Cursor-specific orchestration engine, not portable ideas: TypeScript scripts (`bootstrap.ts`, `orch.ts`, a `watch-pr` CLI), a grok/opus model-routing config (`/setup-pstack`), `make-bot-ui`'s webhook and Tailscale flow, and `cursor-team-kit`-only skills (`deslop`, `control-cli`, `control-ui`) that weren't in this clone. We already have our own role/vendor/adapter design (`docs/roles-and-names.md`, `adapters/README.md`); copying the engine would duplicate it and violate "roles, not vendors." The 24 "principle" skills are a generic engineering-philosophy layer; good content, but out of scope for an orchestration framework about roles, gates and loops. Worth revisiting individually only if a specific leak calls for one.

## Proposed order
A. no-comments as a trial skill on advance-po-reader (prove it the same way F4 was proven, since an untested skill has burned us once already this week); B. swarm's evidence-rejection rule folded into the convergence loop, low risk; C. fresh-subagent-by-default as a protocol note; D and beyond stay later.
