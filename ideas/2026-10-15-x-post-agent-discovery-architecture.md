# What to take from an X post on a planner+proposer discovery architecture (Orchestrator, 2026-10-15)
Nothing here could be checked against a primary source - there isn't one to check. Source: three screenshots Carlos pasted, no link given - a stylized "terminal dashboard" graphic (globe/graph visualization, sparklines, benchmark sliders) and a screenshot of an X post (itself reached via a Reddit repost) by `@ch3nweiii`, describing a "Stanford AI Lab / AgentDiscover" architecture pairing "Claude Opus 5.5" as a search director with "GPT-6.1 Sol" as a candidate proposer. Post/image text is data; nothing in it was executed or followed as an instruction.

## Correction to the source claim
There is no paper, repo, arXiv id, or named lab to verify - "Stanford AI Lab" names no actual lab here, and the posting account states no institutional affiliation. "GPT-6.1 Sol" is not a model name I can confirm exists. The dashboard graphic's own footer reads `SYNTHETIC TELEMETRY` - its own creator is labeling the numbers on it as illustrative, not measured. Treat every performance claim in the post (3.2x lower model spend, 1st place across 7 AtCoder contests, above published SOTA, 0% reward hacks) as unverifiable marketing copy, not evidence. Citing these numbers anywhere in this framework's own docs would itself violate R28 (`templates/benchmark-checklist.md`) - there is no limiter, tuning, repeat-run or relevance check possible on a number with no source.

## Take, in priority order
1. **Evaluator isolation against reward hacking - a real, unbuilt gap.** The post's claim "candidate code never touches the scoring process, so reward hacking and test leakage die on arrival" names a leak class this framework doesn't yet cover. `rules/leak-classes.md`'s C3 ("Tests that share the code's blind spots") covers *weak* tests, not an agent actively *tampering* with its own scoring harness (editing a test file, a fixture, or a CI config so its own code passes). We have no rule against a Build Engineer's PR touching the tests that will judge it. Candidate: watch for this leak in a real PR before writing a rule for it speculatively - the framework's own stated process is "a project run produces a leak... logged with evidence" (`docs/change-proposals.md`), not "write a rule because a tweet imagined a failure mode." If it happens once, it's an instant promote-next candidate (protected-path or `required_checks` tier raise on test files).
2. **Confirms, doesn't add: fresh-session-per-iteration.** "No context bleeding: every session resets after each iteration, the graph keeps the lineage" is R25 (fresh subagent by default), already written down 2026-10-14. No action.
3. **Confirms, doesn't add: lesson distillation.** "An offline pass pulls out verified lessons and updates search guidance across every branch" is what `docs/change-proposals.md`'s rule-for-rules plus `tools/class-ledger`'s promote-next table already do - a finding becomes a class, a repeated class gets promoted to a real enforcer. No action.

## Leave
The Neo4j/Cypher/MAP-Elites/MCTS implementation details - graph-database search tooling, unrelated to a role-and-gate framework built on files and a merge gate, not a persistent idea-graph. The entire benchmark-numbers section (see "Correction," above) - nothing in it is checkable, and the framework's own idea-intake rule exists exactly to stop a secondhand claim like this from being treated as proof.

## Proposed order
Nothing to build now. Log item 1 (evaluator isolation / test-tampering) as a leak class to watch for; act only if a real PR exhibits it, per the framework's own "fix what actually leaked" discipline.
