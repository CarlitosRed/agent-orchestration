# Approval survives a rebase: scope (2026-10-15)
I-005 (`ideas/README.md`), from pstack `autopilot-full`: "an approval stays valid after a rebase or merge-main when the PR's own patch is unchanged." Evidence: PO Reader's PR #20 was re-reviewed three times after merging main, with no code change to review each time (`ideas/2026-10-13-pstack-and-advisor.md`, item 5). Scoping only - nothing below is built, and `cmd_merge`/`evaluate` in `tools/gate/gate.py` are untouched. That logic (the exact-head match at gate.py:824, and the second-look base-move refusal, `WhichDiffTests`) has 227 passing tests riding on its current conservative behaviour and deserves its own dedicated review before anything about it changes.

## What actually happens today
`evaluate()`'s `review` and `owner` rules match an `Approved at <sha>` comment against the PR's *current* `headRefOid` only (gate.py:822-851): `matches = bool(head) and head.startswith(sha)`. Any push - a real code change, a no-op rebase onto a newer `main`, or a `merge main` with no conflicts - changes `headRefOid`, so every approval is immediately re-ignored ("approved an older commit", line 832) and must be re-posted. This is deliberate and currently the *only* behaviour; it is not a bug, it is the thing I-005 asks to relax for one specific case.

## The one case worth relaxing, precisely
"Patch id unchanged" means: the PR's own diff - what it actually changes, independent of which commit it is rebased onto - is byte-identical to what a reviewer already approved. `git patch-id` hashes a diff's content (hunks), not its commit shas or parent, so it is stable across:
1. A clean rebase onto a newer base, no conflicts, no edits.
2. A `merge main` with no conflicts (diff against the new merge-base is unchanged).

It correctly changes - and correctly should force re-review - when a rebase needed any conflict resolution, even a one-character one. The design goal is exact equality, not a fuzzy match; a scheme that approximates this would be worse than today's conservative default.

## Why this needs real git, not more `gh` JSON
`git patch-id` has to run against the literal diff bytes of two real commits: the sha that was approved, and the current head. GitHub's REST API doesn't expose that: `gh api repos/.../commits/<sha>` returns a per-file `patch` field that is a truncated, line-numbered fragment (capped around 500 lines per file), not byte-identical to `git diff`'s output - feeding it to `git patch-id` would not reproduce the real id. The only correct source is an actual `git diff <merge-base>..<head> | git patch-id` against real commit objects. `gate.py` already shells out to local `git` today (`run_git`, gate.py:467) for `scan` and `audit`, which read the current working tree and already-fetched history - but the `review`/`owner` path in `evaluate()` is pure `gh`-JSON today and has never needed a local object before. This would be the first time `check`/`merge` depend on git objects existing locally, which is new, not incidental.

## The sharp edge: the approved commit may already be gone
After a force-push rebase, the approved sha is usually unreachable from any ref on the remote. GitHub does not promise to keep an unreachable commit fetchable indefinitely - some hosts disable fetching arbitrary shas outright (`uploadpack.allowReachableSHA1InWant`/`allowAnySHA1InWant`), and even where it's allowed, a quiet, undocumented repo GC can prune it later. Concretely, this means the design cannot be "compute the patch id lazily, whenever `check`/`merge` runs" - by the time someone runs `check`, the approved sha may no longer be fetchable at all. The patch id has to be **captured and stored the moment the approval is read as valid**, not recomputed from the historical sha later.

## Split, the way claims-ledger's ask was split
1. **Tractable, buildable on its own, zero interaction with `cmd_merge`:** a pure helper, same shape as `claims.py`'s `changed_lines()` - stdlib `subprocess` only, real throwaway git repos in its tests, no mocking. Working name `patch_id_of(base_sha, head_sha, cwd)`: runs `git diff <base_sha>..<head_sha> | git patch-id --stable` and returns the id (the first whitespace-separated token), raising `Broken` if either sha is not already a locally known object. It never fetches - whether to fetch, from where, and under what safety rule is a separate, harder question, scoped out below. This piece could be written and tested today without touching `gate.py` at all.
2. **Where it would have to plug in, which is explicitly NOT this pass:** the instant the `review` rule in `evaluate()` currently passes, the gate would need to also snapshot `(signer, approved head sha, base sha at that moment, patch id)` somewhere durable, before the approved sha has any chance of becoming unfetchable. That touches the exact 227-test code path the handoff said to leave alone, and needs its own careful round: where the record lives (a new small ledger under `tools/`, a comment the gate itself posts back to the PR, something under `.orchestration/`), and how `review`/`owner` would then accept either an exact head match (today's rule, unchanged) *or* a stored patch-id match against the current head's own diff against the current base.
3. **Not scoped at all yet, left for whoever picks this up next:** whether `check`/`merge` should ever attempt a `git fetch` for a sha it doesn't have locally (and under what guard - fetching arbitrary shas from CI has its own risk surface); how a merge-commit rebase (two parents) picks the right merge-base to diff against, as opposed to a plain linear rebase; whether this is a Tier-3 change (it touches `tools/gate/*`, a protected path per `gate.schema.md`'s example config) and what proof (`docs/change-proposals.md`'s `## Proof`) would show it actually cut re-review rounds on a real PR.

## Unsure
1. `git patch-id --stable` is the right flag (stable ids across git versions) but this was not run against a real conflicted-then-resolved rebase to confirm the id actually changes as expected - worth a throwaway-repo test before trusting the "correctly re-reviews on any real edit" claim.
2. Whether GitHub's own GC timeline for unreachable commits is long enough in practice that "capture eagerly" is being overcautious - not measured, no documented SLA found; the design above treats it as unsafe to assume either way.
3. Whether a merge-main (not rebase) case is common enough in this framework's own workflow (branch-and-PR, no local merges) to be worth the merge-base complexity in item 3 above, versus scoping the first cut to plain rebases only.
