# Vendor count: one, two, or more (scope, 2026-10-15)
Carlos's ask: let a project run on exactly one vendor (Codex only, or Claude only, or Gemini only), on two (today's default: Codex + Claude), or on three-plus (Codex + Claude + Gemini, all working together) - as one flexible spec, not three separate frameworks - with the limitations of running fewer vendors written down plainly, not silently accepted. Scoping only. Nothing in `tools/gate/gate.py` changes; the mechanism the single-vendor case needs already exists and is tested.

## What already works today, unchanged
Two or more vendors needs no new code. `gate.json`'s `vendors` field is already an arbitrary-size map (`gate.schema.md`: `vendor id -> {names, branch_prefixes}`), and the gate's independence check (`gate.py:812`, `independent()`) is `signer.vendor != a_vendor` - true for ANY vendor that is not the author's, not hardcoded to "the one other vendor." Adding a third (Gemini, or any other) is just another `vendors/` capability profile plus another entry in `gate.json`, the same shape `vendors/codex.md` and `vendors/claude-code.md` already are. The real constraint today is proof, not code: Codex is live-tested (`vendors/codex.md`'s smoke test), Claude Code is written but never exercised (blocked on `claude auth login`), and no third vendor has ever been tried (F7's own stated goal, still open).

## What's genuinely new: exactly one vendor
The mechanism exists and is tested, just never documented as a deliberate mode or used by any project: `cross_vendor: false` on a tier, plus a NAMED allowlist in `same_vendor_reviewers` (`gate.schema.md` line 44; `tools/gate/test_gate.py`'s `SameVendorOptionTests`, 3 passing tests). It is not "anyone from the same vendor" - `test_an_unlisted_signer_of_the_same_vendor_never_counts` confirms an unlisted signer of the author's own vendor is refused exactly like today. What it buys a single-vendor project: two distinct, named identities (for example two separately-launched sessions of the same vendor, one building, one reviewing) must still both sign, rather than literal self-approval. What it does **not** buy: genuine independence. Two sessions of the same model family share training data, systematic blind spots, and correlated failure modes that a different vendor's review exists specifically to catch - this is the exact thing `docs/framework-map.md` names as the reason R21 exists ("the author's vendor never reviews alone and the other vendor reviews; same-vendor second opinions only as extra"). A single-vendor project cannot have that property by construction, no matter how the config is written.

## Limitations to write down, explicitly, for a single-vendor project
1. **No cross-vendor review signal.** The convergence loop's "a class raised by both vendors is top priority" (`docs/convergence-loop.md`) has no single-vendor equivalent; two same-vendor reviews agreeing is correlated evidence, not independent confirmation, and should never be reported or felt as the same strength of signal.
2. **A vendor-specific outage is a single point of failure.** A real, already-logged example: Codex's Windows shell-exec bug (`vendors/codex.md`) had a working fallback (the manual paste-relay path, a different vendor doing the automated side) only because a second vendor existed. A single-vendor project has no vendor to route around an outage like that.
3. **The compensating control is an open question, not decided here** - see below.

## Open question for Carlos
Whether a single-vendor project should be required to raise `owner_approval` at a lower tier than a multi-vendor project needs it - pulling the Program Owner in more often to structurally compensate for the missing cross-vendor check - or whether `same_vendor_reviewers`'s existing two-distinct-identities requirement is enough on its own, leaving the owner-approval threshold exactly where it is today (tier 3 only). This is a real tradeoff between safety and friction for anyone who actually runs single-vendor, and I don't want to guess which one you'd pick.

## Proposed shape, not yet built
- `adapters/README.md` gets a new "How many vendors" section: two-or-more (today's docs apply as written, no change needed) and exactly-one (points here, names the limitations above, requires `same_vendor_reviewers` plus whatever the owner-approval answer above turns out to be).
- `docs/roles-and-names.md`'s Independent Reviewer row and `docs/tiers-and-approvals.md`'s "one, from the other vendor" language get a one-line pointer to the single-vendor exception, not a rewrite - the two-vendor case stays the default, documented exactly as it is today.
- A real third vendor, if wanted: `vendors/gemini.md`, built and live-smoke-tested the same way `vendors/codex.md` and `vendors/claude-code.md` were - a new profile, not a framework change, confirming the "two or more needs no new code" claim above on contact with reality.

## Status
Scoped only, 2026-10-15. `tools/gate/gate.py` is unchanged - the single-vendor mechanism it relies on was already built and tested, just never used or documented as this. The one real decision left is the compensating-control question above.
