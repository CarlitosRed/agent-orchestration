# Project adapter spec (what a project provides to run on the framework)
Each project keeps a folder `.orchestration/` with:
- `framework.pin`: the framework version (git tag) the project runs on.
- `gate.json`: the config of `tools/gate/gate.py`, schema in `tools/gate/gate.schema.md`. Required: `schema_version`, `tiers` (label, level, approvals, plan_go, owner_approval, cross_vendor, body_headings, allowed_paths, mergeable, record), `vendors` (names, branch_prefixes), `owner_signers`, `protected_paths`, `protected_tier`, `required_checks`. Optional: `legacy_signers` (old signature names during migration), `forbidden_head_prefixes`, `body_headings`, `verdict_sha_min_length`, forbidden-file and secret lists. Who merges is fixed: the author's vendor (by branch prefix) or the owner.
- `desk.md`: facts about the machine and environment (interpreters, services, ports, known flakes).
- `commands.md`: the exact commands for tests, scan and the app launcher; for the verification drive it points at `verify/SKILL.md` instead of repeating it.
- `roles.md`: which vendor and model fills each role in this project and the launch limits (usage ceilings).
- `leaks.md`: the project's leak log (what went wrong, evidence, root cause, fix).
- `verify/`: the project's verification skill (below).
A project is "on the framework" when its gate runs from the pinned tool with this config. Status: advance-po-reader has these facts spread across `tools/gate`, `desk-environment.md`, `ROLES.md`; career-agent-hq has its own early copies of the rules. F2 and F5 move both onto this spec.

## Verification (`.orchestration/verify/`)
Generated by `skills/create-verification-skill`, kept current by `skills/maintain-verification-skill`, used by `skills/record-demo`. Both skills call the shared `tools/verify-manifest/manifest.py` (standard library only) to hash evidence, check survival after cleanup, and resolve the project root from a script's own path, instead of each project re-deriving that logic by hand. Shape:
```
.orchestration/verify/
  SKILL.md           name + description frontmatter; sections: Terms, Surfaces, Launch, Doctor, Drive,
                     Evidence, Data, Safe mode, Cleanup and teardown, Features, Unmapped, Proof record
  features/<slug>.md one per user-facing feature; slug = lowercase and hyphens; sections: Purpose,
                     How to reach it, Setup, How to drive it, Proof (visible end state + side effects),
                     Evidence to capture, Cleanup, Pointers, Demo caption (optional); first lines carry
                     slug, surface and status (proven at <sha> on <date> | unproven | broken)
  fixtures/          optional; synthetic data only
  .gitignore         contains evidence/
  evidence/          run folders <UTC yyyymmdd-hhmmss>-<proof|maintain|demo>/ with manifest.json; never committed
```
Required: `SKILL.md` with a passing proof record, and at least one feature file. A library-only project's primary surface is its public API, driven by an example program in `fixtures/`. Changes to `verify/` go through the project's normal PR process (Tier 1 or 2 by the project's `gate.json`; the framework does not set it). Status: PROPOSED until the first project generates and proves one.
