# Project adapter spec (what a project provides to run on the framework)
Requirements only. Dated observations and project status live in `docs/adapter-history.md`; current state is read from the repos (`STATE.md`).

Each project keeps a folder `.orchestration/` with:
- `framework.pin`: the framework repo's URL and the git tag the project runs on, two lines (`repo: <url>` then `tag: <tag>`). The repo URL doubles as the address of the handoff bus (below); do not guess it from memory. To use the pinned tool (`tools/gate/gate.py`, a skill, a template), shallow-clone the framework repo at that tag (`git clone --depth 1 --branch <tag> <repo>`) rather than a submodule or a package install: no packaging exists, and a shallow clone needs nothing beyond git. `templates/gate-pre-review.yml` and `templates/gate-audit.yml` do this, plain by default with an authenticated fallback (see "Private framework repo access" below).
- `gate.json`: the config of `tools/gate/gate.py`, schema in `tools/gate/gate.schema.md`. Required: `schema_version`, `tiers` (label, level, approvals, plan_go, owner_approval, cross_vendor, body_headings, allowed_paths, mergeable, record), `vendors` (names, branch_prefixes), `owner_signers`, `protected_paths`, `protected_tier`, `required_checks`. Optional: `legacy_signers` (old signature names; a project may use these permanently and never adopt `<Role> · <Vendor>` signatures - "legacy" names the format, not a required transition), `forbidden_head_prefixes`, `body_headings`, `verdict_sha_min_length`, forbidden-file and secret lists (if a project's own existing gate already enforces these, diff the two lists before switching real enforcement onto the generic gate). Who merges is fixed: the author's vendor (by branch prefix) or the owner.
- `desk.md`: facts about the machine and environment (interpreters, services, ports, known flakes).
- `commands.md`: the exact commands for tests, scan and the app launcher; for the verification drive it points at `verify/SKILL.md` instead of repeating it. A documents-only project (output is files, not an app or library) has no launcher line; it points at its own evidence or decision log instead (see "Verification").
- `roles.md`: which vendor and model fills each role in this project and the launch limits (usage ceilings): the window (`5h`/`7d`) and the ceiling number, in whatever unit this project logs; checked with `tools/usage-ledger/usage.py check` (R14).
- `leaks.md`: the project's leak log (what went wrong, evidence, root cause, fix).
- `verify/`: the project's verification skill (below).

A file here may be a pointer, not a copy. `desk.md` and `leaks.md` in particular may already be real, actively written files elsewhere (for example a sibling private ops repo). A short pointer file naming the real location is enough, and is often better than duplicating a file something else reads from its current path.

## CI workflows
Alongside `.orchestration/`, a project copies two workflows into its own `.github/workflows/`, both required:
- `templates/gate-pre-review.yml`: runs the gate's dry run when a PR opens or changes, and again when its labels, body or draft state change (R16). It reads the pin and `gate.json` from the PR's base commit, so a PR cannot loosen the rules it is judged by.
- `templates/gate-audit.yml`: after every push to main, checks that each new commit carries a Gate-Record line and opens an issue if not. It reads the pin and `gate.json` from the commit before the push. **This is a detective control, not a preventive one:** it cannot stop a bad push or a click on the host's merge button, only report one within minutes. GitHub branch protection would be preventive but needs a public repo or a paid plan.

A copied workflow is not updated by a framework release; a project updates its copies by its own PR at a new pin.

### Private framework repo access
A public framework pin is cloned without a secret. A pin pointing at a private repo needs a project secret named exactly `FRAMEWORK_PIN_TOKEN` (a read-only token created by the Program Owner, never by an agent). Both templates try a plain clone first, fall back to the token, and fail with a named error when neither works. Full text: `docs/private-framework-access.md`.

## On the framework
A project is "on the framework" when its gate runs from the pinned tool with this config AND both workflows above are installed and have run. A `gate.json` with no wired CI behind it is a documentation-only restatement, not enforcement.

## Verification (`.orchestration/verify/`)
Generated by `skills/create-verification-skill`, kept current by `skills/maintain-verification-skill`, used by `skills/record-demo`. Both skills call the shared `tools/verify-manifest/manifest.py` (standard library only) to hash evidence, check survival after cleanup, and resolve the project root from a script's own path. Shape:
```
.orchestration/verify/
  SKILL.md           name + description frontmatter; sections: Terms, Surfaces, Launch, Doctor, Drive,
                     Evidence, Data, Safe mode, Cleanup and teardown, Features, Unmapped, Proof record
  features/<slug>.md one per user-facing feature; slug = lowercase and hyphens; sections: Purpose,
                     How to reach it, Setup, How to drive it, Proof (visible end state + side effects),
                     Evidence to capture, Cleanup, Pointers, Demo caption (optional); first lines carry
                     slug, surface and status (proven at <sha> on <date> | unproven | broken)
  fixtures/          optional; synthetic data only
  .gitignore         contains evidence/
  evidence/          run folders <UTC yyyymmdd-hhmmss>-<proof|maintain|demo>/ with manifest.json; never committed
```
Required: `SKILL.md` with a passing proof record, and at least one feature file. A library-only project's primary surface is its public API, driven by an example program in `fixtures/`. Changes to `verify/` go through the project's normal PR process (Tier 1 or 2 by the project's `gate.json`; the framework does not set it).

**Documents-only projects are exempt from the folder above.** A project whose output is files, not a running app, API or library has no `verify/` to generate. `commands.md` points instead at the project's own evidence or decision log - one entry per claim, with what proves it - as the equivalent proof step; a reviewer checks that log the way they would check a proof record.

## How many vendors
A project's `gate.json` `vendors` map may name one vendor, two (today's default) or more; the gate's independence check (`tools/gate/gate.py`'s `independent()`) is vendor-count-agnostic, so two or more needs only another `vendors/` capability profile and another `vendors` entry. Exactly one vendor is a supported mode that loses something on purpose written down here (full scoping: `docs/vendor-count-modes.md`).

A single-vendor project:
- sets `cross_vendor: false` on every tier that needs review, and names two distinct, specific identities in `same_vendor_reviewers` (not "anyone from the vendor": an unlisted signer of the author's own vendor is still refused) - for example two separately launched sessions of the same vendor, one building, one reviewing;
- sets `owner_approval: true` on every tier that requires any `approvals`, not only the tier that would otherwise need it. This is a deliberate compensating control: with no cross-vendor check to catch a single vendor's correlated blind spots, the Program Owner's sign-off is pulled in more often;
- carries as a standing fact: no cross-vendor review signal, ever, and a vendor outage is a single point of failure with no fallback vendor.

## Handoff (cross-orchestrator messages)
Generated and checked by `skills/handoff`; design in `docs/vendor-neutral-handoff.md`. The framework repo named in the project's `framework.pin` is the shared bus (GitHub issues labeled `handoff`, `to:<slug>` or `from:<slug>`); every orchestrator checks it first in its sweep. No per-project file or config beyond the repo URL already in `framework.pin`.
