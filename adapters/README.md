# Project adapter spec (what a project provides to run on the framework)
Each project keeps a folder `.orchestration/` with:
- `framework.pin`: the framework repo's URL and the git tag the project runs on, two lines (`repo: <url>` then `tag: <tag>`). The repo URL doubles as the address of the handoff bus (below); do not guess it from memory. To actually use the pinned tool (`tools/gate/gate.py`, a skill, a template), shallow-clone the framework repo at that tag (`git clone --depth 1 --branch <tag> <repo>`) rather than a submodule or a package install - no packaging exists yet, and a shallow clone needs nothing beyond git itself, which every CI runner and every vendor's agent already has. `templates/gate-pre-review.yml` does exactly this.
- `gate.json`: the config of `tools/gate/gate.py`, schema in `tools/gate/gate.schema.md`. Required: `schema_version`, `tiers` (label, level, approvals, plan_go, owner_approval, cross_vendor, body_headings, allowed_paths, mergeable, record), `vendors` (names, branch_prefixes), `owner_signers`, `protected_paths`, `protected_tier`, `required_checks`. Optional: `legacy_signers` (old signature names; a project may use these permanently and never adopt `<Role> · <Vendor>` signatures at all - "legacy" names the format, not a required transition), `forbidden_head_prefixes`, `body_headings`, `verdict_sha_min_length`, forbidden-file and secret lists (if a project's own existing gate already enforces these, diff the two lists before ever switching real enforcement onto the generic gate - do not assume they match). Who merges is fixed: the author's vendor (by branch prefix) or the owner.
- `desk.md`: facts about the machine and environment (interpreters, services, ports, known flakes).
- `commands.md`: the exact commands for tests, scan and the app launcher; for the verification drive it points at `verify/SKILL.md` instead of repeating it. A documents-only project (nothing to launch - output is files, not an app or library) has no launcher line; it points here at its own evidence or decision log instead (see "Verification", below).
- `roles.md`: which vendor and model fills each role in this project and the launch limits (usage ceilings) - the window (`5h`/`7d`) and the ceiling number, in whatever unit this project logs (launches by default, or a real token count); checked with `tools/usage-ledger/usage.py check` (R14).
- `leaks.md`: the project's leak log (what went wrong, evidence, root cause, fix).
- `verify/`: the project's verification skill (below).

**A file here may be a pointer, not a copy.** `desk.md` and `leaks.md` in particular are sometimes already real, actively-written files in a sibling private ops repo that predates the framework (one project's pattern: a separate `project-notes` repo). The adapter spec does not require moving them - a short pointer file naming the real location is enough, and is often the right call over duplicating a file something else already depends on reading from its current path. Found by `retrofit-project`'s first real run (2026-10-15): do not assume one-repo-per-project everywhere this spec is read.

A project is "on the framework" when its gate runs from the pinned tool with this config. Status: advance-po-reader retrofitted 2026-10-15 (advance-po-reader#51, open for its own tier-3 review); career-agent-hq not yet started.

## Verification (`.orchestration/verify/`)
Generated by `skills/create-verification-skill`, kept current by `skills/maintain-verification-skill`, used by `skills/record-demo`. Both skills call the shared `tools/verify-manifest/manifest.py` (standard library only) to hash evidence, check survival after cleanup, and resolve the project root from a script's own path, instead of each project re-deriving that logic by hand. Shape:
```
.orchestration/verify/
  SKILL.md           name + description frontmatter; sections: Terms, Surfaces, Launch, Doctor, Drive,
                     Evidence, Data, Safe mode, Cleanup and teardown, Features, Unmapped, Proof record
  features/<slug>.md one per user-facing feature; slug = lowercase and hyphens; sections: Purpose,
                     How to reach it, Setup, How to drive it, Proof (visible end state + side effects),
                     Evidence to capture, Cleanup, Pointers, Demo caption (optional); first lines carry
                     slug, surface and status (proven at <sha> on <date> | unproven | broken)
  fixtures/          optional; synthetic data only
  .gitignore         contains evidence/
  evidence/          run folders <UTC yyyymmdd-hhmmss>-<proof|maintain|demo>/ with manifest.json; never committed
```
Required: `SKILL.md` with a passing proof record, and at least one feature file. A library-only project's primary surface is its public API, driven by an example program in `fixtures/`. Changes to `verify/` go through the project's normal PR process (Tier 1 or 2 by the project's `gate.json`; the framework does not set it). Status: PROPOSED until the first project generates and proves one.

**Documents-only projects are exempt from the folder above.** A project whose output is files, not a running app, API or library (career-agent-hq: CV and LinkedIn drafts, evidence entries - nothing to launch or drive like a user) has no `verify/` to generate at all. `commands.md` points instead at the project's own evidence or decision log - one entry per claim, with what proves it - as the equivalent proof step; that log is the thing a reviewer actually checks, same job `verify/`'s Proof record does for a launchable project. First instance: career-agent-hq's retrofit (`career-agent-hq#1`), which found this gap and pointed `commands.md` at its own `evidence/E-###` entries before this exemption was written down (`agent-orchestration#36`). Status: specified - nothing to prove, since there's no tool to run, only a pointer to point at what the project already keeps.

## How many vendors
A project's `gate.json` `vendors` map may name one vendor, two (today's default: Codex + Claude), or more; the gate's own independence check (`tools/gate/gate.py`'s `independent()`) is vendor-count-agnostic, so two-or-more needs nothing beyond another `vendors/` capability profile and another `vendors` entry - the rest of this spec and `docs/roles-and-names.md` / `docs/tiers-and-approvals.md` apply exactly as written. Exactly one vendor is a real, supported mode, not an unsupported edge case - but it genuinely loses something, written down on purpose rather than left for someone to discover the hard way (full scoping: `docs/vendor-count-modes.md`).

A single-vendor project:
- sets `cross_vendor: false` on every tier that needs review, and names two distinct, specific identities in `same_vendor_reviewers` (not "anyone from the vendor" - an unlisted signer of the author's own vendor is still refused, same as a two-vendor project) - for example two separately-launched sessions of the same vendor, one building, one reviewing;
- additionally sets `owner_approval: true` on every tier that requires any `approvals`, not only the tier that would otherwise need it (today's default tier shape needs it starting at tier 3 only; a single-vendor project's tier 2 behaves like tier 3's owner-approval requirement instead). Carlos's own call, 2026-10-15: a deliberate compensating control, since there is no cross-vendor check to catch what a single vendor's correlated blind spots miss, so the Program Owner's own sign-off is pulled in more often instead.
- carries, as a standing fact about the project rather than a one-time warning: no cross-vendor review signal, ever, and a vendor outage is a single point of failure with no fallback vendor to route around it.

## Handoff (cross-orchestrator messages)
Generated and checked by `skills/handoff`; design in `docs/vendor-neutral-handoff.md`. The framework repo named in this project's own `framework.pin` is the shared bus (GitHub issues, labeled `handoff`, `to:<slug>` or `from:<slug>`); every orchestrator checks it as the first step of its own sweep. No per-project file or config beyond the repo URL already in `framework.pin`. Status: designed, not yet exercised on a real cross-vendor handoff.
